1. FINALITÉ, PUBLIC ET CHOIX VALIDÉS
==================================

Le projet est parti d’un classeur annuel de séances et d’un document explicatif
pour obtenir un planning facile à consulter, avec des allures personnalisées.
La solution retenue est un site internet classique hébergé, avec une base commune
et des sessions individuelles. Ce n’est pas un simple fichier partagé.

Le groupe est petit. Le lien est diffusé en interne. L’utilisatrice souhaite une
solution gratuite et peu contraignante, entretenable après son départ du club.
Le site est également installable comme application web sur téléphone (PWA).

Choix successifs, à lire selon leur ordre de validation :
- Les comptes uniquement locaux au téléphone n’ont pas été retenus : les profils
  et contenus doivent être synchronisés en ligne.
- Une version avec identifiant seul a existé, mais des mots de passe ont ensuite
  été ajoutés. La version actuelle utilise identifiant ET mot de passe.
- Aucun minimum de complexité ni de longueur de mot de passe n’est demandé,
  hormis un mot de passe non vide et les limites techniques de saisie.
- Toute nouvelle inscription au groupe exige le code de groupe. Choisir coach
  demande également le code coach, à l’inscription ou plus tard dans Réglages.
- Les deux codes sont sensibles à la casse, communs à tous les admins, visibles
  en clair dans leurs réglages, et modifiables à tout moment par un admin.
  Valeurs initiales : `NOUVEAU` et `COACH`. Remplacer un code invalide aussitôt
  son ancienne valeur pour toutes les inscriptions/demandes suivantes.
- L’activation initiale du compte admin ne demande pas le code de groupe.
- Les admins peuvent nommer ou retirer des coachs depuis la gestion des membres.
- Le rôle admin ne donne pas automatiquement le rôle coach.
- Render n’est pas l’hébergement retenu : utiliser Cloudflare Pages et D1.
- La suppression automatique après trois mois a été expressément retirée.

4. COMPTES, CONNEXION ET DONNÉES PERSONNELLES
==========================================

4.1 Connexion
- Toute ouverture ou actualisation du lien demande une connexion.
- La navigation interne entre les onglets garde la session active.
- Le jeton est conservé dans la mémoire de la page, pas comme une connexion
  persistante permettant de contourner la demande au prochain rechargement.
- Le serveur donne actuellement des sessions temporaires de 12 heures.
- L’accès à l’API des données nécessite une session valide.
- La coque de connexion et les fichiers statiques peuvent être publics ; les
  données de l’équipe ne doivent pas être publiées comme fichiers statiques.

4.2 Inscription
- Lien « Inscription » accessible sans être déjà membre.
- Champs : prénom, nom, téléphone facultatif, identifiant, mot de passe,
  code du groupe, case « Je suis coach » et code coach si elle est cochée.
- Le prénom, l’identifiant et le mot de passe sont requis ; le nom et le
  téléphone peuvent être laissés vides dans l’implémentation actuelle.
- Le code de groupe est requis pour tout nouveau compte ; le code coach est
  requis seulement si le rôle coach est demandé à l’inscription.
- L’activation initiale du profil admin préconfiguré ne demande pas ces codes.
- Les codes initiaux sont `NOUVEAU` (groupe) et `COACH` (coach), sensibles à la
  casse. Les admins peuvent les consulter en clair et les modifier dans Réglages.
  Les deux valeurs sont partagées entre tous les admins ; une modification
  remplace immédiatement l’ancienne valeur.
- Un athlète peut aussi demander le rôle coach depuis Réglages en saisissant le
  code coach ; un coach peut retirer lui-même ce rôle sans code.
- Tous les codes sont comparés sans normalisation, sensibles aux majuscules et
  minuscules. Le code de groupe est obligatoire pour créer un nouveau compte.
- Un compte ne peut jamais s’auto-attribuer le rôle admin à l’inscription.

4.3 Identifiants et mots de passe
- Respect exact des majuscules et minuscules.
- L’identifiant doit être unique avec cette règle : Alice et alice sont donc
  deux identifiants distincts, mais deux occurrences exactes de Alice sont refusées.
- Une collision à l’inscription ou au changement d’identifiant renvoie une erreur.
- Les identifiants existants n’ont pas été uniformisés ou passés en minuscules.
- Le champ technique « email » désigne ici l’identifiant : ce n’est pas forcément
  une adresse de courrier électronique.
- Le changement d’identifiant ne crée pas un nouveau profil et ne change pas
  automatiquement le mot de passe ; l’id interne du compte reste identique.
- Les mots de passe ne sont pas nettoyés en minuscules et les espaces y comptent.
- Limite actuelle de mot de passe : 1024 caractères ; pas de règle de complexité.
- Stockage : PBKDF2 SHA-256, sel aléatoire, 100 000 itérations, jamais un mot de
  passe personnel envoyé dans la liste des membres ou dans /api/state.
- Pour les anciens comptes sans mot de passe, le mot de passe provisoire est
  l’identifiant exact capturé lors de la migration. Une migration ultérieure ne
  doit pas réinitialiser le mot de passe déjà choisi par le membre.

4.4 Données personnelles
- Chaque athlète, coach et admin a ses propres chronos.
- Les allures affichées sont calculées pour la personne connectée.
- Les chronos d’un coach ne changent jamais ceux des athlètes.
- Aucun endpoint actuel n’autorise la consultation/modification des chronos
  d’un autre membre, y compris par un admin.
- Réglages personnels : identifiant, prénom, nom, téléphone, mot de passe,
  demande ou retrait du rôle coach par une case dédiée, consultation du rôle et
  suppression de son propre profil. Devenir coach exige le code coach ; le retirer
  n’exige pas de code. Les admins voient et modifient les deux codes partagés.
- Les rôles ne se modifient pas via le formulaire d’identité personnel.
- Le téléphone est visible dans l’annuaire du groupe connecté et reste facultatif.

4.5 Date d’ajout des comptes
- Colonne « Ajout du compte » dans Le groupe et dans la gestion admin.
- Affichage actuel : jour/mois/année, sans heure.
- Les créations postérieures à l’ajout de cette fonction ont une date stockée
  sous forme de timestamp ; un déclencheur SQL l’enregistre à l’insertion.
- Les comptes antérieurs n’ont pas de date historique connue : « Non renseignée ».
- Ne jamais leur attribuer artificiellement la date de migration ou de déploiement.
- Une réinitialisation de mot de passe ou un changement d’identifiant ne change
  pas la date de création du compte.


5. MATRICE DE DROITS ET TRANSMISSION DU SITE
==========================================

Tous les profils connectés peuvent :
- Lire le planning, les périodes, la bibliothèque et les infos du groupe.
- Gérer leurs propres chronos, identité, mot de passe et compte.
- Lire les coordonnées des membres dans l’annuaire.
- Ajouter/modifier/retirer des compétitions, même créées par un autre membre.
- S’inscrire personnellement aux compétitions et voir la liste publique des inscrits.
- Ajouter/modifier/supprimer leurs propres commentaires de séance.

Athlète :
- Pas de modification des séances, circuits, infos ou périodes communes.
- Pas de modification d’un autre compte ou de ses commentaires.

Coach :
- Tous les droits communs, plus créer/modifier/déplacer/échanger/archiver les séances.
- Créer/modifier/archiver les acronymes, circuits et informations du groupe.
- Gérer les périodes, charges, vacances, absences, stages et notes de saison.
- Lire les notes coach et les commentaires privés destinés aux coachs.
- Aucun droit d’administration sur les comptes des autres membres.

Admin :
- Tous les droits communs, plus gestion des comptes et attribution des rôles.
- Nommer des admins, retirer ces droits, nommer des coachs ou retirer leurs droits.
- Consulter et mettre à jour les codes d’accès au groupe et le code coach ; les
  nouvelles valeurs sont communes à tous les admins et invalident les anciennes.
- Les valeurs des codes sont incluses uniquement dans l’état envoyé aux admins ;
  elles ne sont jamais envoyées aux profils athlète ou coach.
- Supprimer les comptes d’autres membres, y compris coachs ou autres admins,
  à condition qu’il reste au moins un admin.
- Réinitialiser le mot de passe d’un autre compte en choisissant lui-même un
  nouveau mot de passe provisoire ; déconnexion de toutes les sessions du membre.
- Accès aux identifiants nécessaires à la gestion, mais pas aux chronos d’autrui.
- Pas d’édition des séances ou périodes uniquement du fait du rôle admin.
- Pas d’accès aux commentaires privés d’autres membres uniquement du fait du
  rôle admin : la règle est auteur + coachs, pas auteur + coachs + admins.

Les trois rôles sont actuellement exclusifs, pas des droits cumulables. La case
personnelle de rôle coach est disponible aux profils athlète et coach ; un admin
utilise la gestion des membres pour modifier les rôles, afin de préserver le
dernier compte admin. Un admin peut attribuer directement le rôle coach à un
autre membre depuis Gestion des membres ; le code coach protège les demandes
d’auto-attribution à l’inscription et dans les réglages.
Nommer un coach admin remplace son rôle coach. Retirer les droits admin lui
rend son rôle précédent, coach ou athlète.

Premier compte admin prévu : Maylis Chancerelle, avec activation initiale dédiée.
Pour transmettre le site : nommer un successeur admin déjà inscrit, vérifier son
accès, puis retirer ses propres droits ou son compte si nécessaire.
Il faut distinguer deux transmissions :
- Admin du site : gère le groupe dans l’interface.
- Accès à GitHub et Cloudflare : entretient le code, l’hébergement et les sauvegardes.
Nommer un admin dans le site ne lui donne pas automatiquement accès à ces services.

Actions admin dans Réglages → Gestion des membres :
- Tableau membre, identifiant, date d’ajout, profil, droits et actions de compte.
- Boutons Nommer admin / Retirer les droits admin.
- Boutons Nommer coach / Retirer les droits coach pour les non-admins.
- Réinitialiser le mot de passe : fenêtre de saisie d’un mot de passe non vide,
  confirmation, puis affichage du nouveau mot de passe provisoire à transmettre.
- Supprimer le compte : fenêtre explicite et case « Êtes-vous sûr de vouloir
  supprimer ce compte ? », puis bouton de suppression définitive.
- Pas de saisie d’identifiant à recopier dans cette confirmation visuelle.
  Le client transmet néanmoins l’identifiant du compte ciblé à l’API pour contrôle.
- Pour son propre mot de passe ou sa suppression, l’admin utilise ses formulaires
  personnels, comme les autres profils.
- La suppression efface compte, chronos, coordonnées, sessions, mots de passe,
  commentaires, inscriptions et date d’ajout. Le contenu partagé est conservé.
- Aucune mise à jour du code ne doit exécuter ces actions sur les vrais membres.


6. SÉANCES ET CALENDRIER
=======================

Structure d’une séance :
- id interne stable, titre, date, type et créneau.
- Créneau : matin, après-midi, soir ou non précisé.
- Échauffement, puis Séance.
- Version 2 facultative dans un encadré vert, affichée directement si présente.
- Cibles d’allure : distance et pourcentage, ou intervalle de chronos fixes.
- Étiquette facultative pour une cible, par exemple Filles, Garçons ou Tous.
- Charge : héritée de la semaine, spécifique à la séance, ou masquée.
- Cycle et notes coach, lorsqu’ils sont renseignés.
- Bouton Commenter et synthèse des difficultés publiques.

Plusieurs séances le même jour sont possibles, notamment matin et après-midi.
Un jour initialement de repos peut recevoir une séance ; la carte Repos importée
est alors masquée si une séance active existe, sans être nécessairement supprimée.
Une journée vide signifie « aucune séance renseignée », pas un repos inventé.

Déplacement : modifier uniquement la date et éventuellement le créneau, sans
ressaisir le contenu. Échange : permuter deux séances et leurs créneaux dans
une transaction, avec vérification de versions. Les commentaires suivent l’id
de la séance, donc restent attachés à celle-ci après son déplacement.

Calendrier :
- Sélection initiale de la date courante.
- Calendrier mensuel défilant, jours cliquables.
- Navigation de semaine avec flèches, conservant le même jour de la semaine.
- Couleurs et libellés des séances ; représentation de plusieurs séances par jour.
- Indications contextuelles des semaines : charge, intensité, vacances, stages,
  compétition, en complément des cartes quotidiennes.
- Le calendrier mensuel fonctionne sans limite fixe, donc après août 2028.
- Les séances importées couvrent initialement le 28 septembre 2026 au
  23 janvier 2027. Ne pas fabriquer des séances pour remplir la suite.

Conservation : le coach peut archiver une séance, mais il n’y a plus de purge
automatique à trois mois ou lorsque la base se remplit. L’archivage des contenus
utilise archived=1 et conserve les données en base. Une ancienne purge ayant déjà
supprimé des données ne peut pas être annulée sans une sauvegarde antérieure.

8. CHRONOS ET MODÈLE DE FATIGUE : SPÉCIFICATION EXACTE
===================================================

L’onglet Mes chronos regroupe calculateur et références personnelles.
Ordre validé : calculateur d’abord, saisie des chronos ensuite.
Distances personnelles disponibles : 50, 60, 80, 100, 125, 150, 200, 250, 300,
400, 500, 600, 800, 1000 et 1500 mètres. Des champs peuvent rester vides.
Formats : secondes avec virgule ou point, par exemple 54,32 ou 54.32 ; minutes
et secondes, par exemple 1:02,50. Les données sont stockées en secondes.

Objectif : un chrono au 100 et/ou au 200 et au 400 doit permettre d’estimer une
référence sur une autre distance, notamment 250 m. Tous les chronos connus doivent
primer sur une courbe générique et appartenir exactement à la courbe personnelle.

Lecture de la feuille Temps du coach :
- Grilles indépendantes par distance : colonne de référence à gauche, colonnes
  de temps cibles à droite pour différentes intensités.
- Le calcul de pourcentage passe par la vitesse en m/s.
- Les lignes de différents tableaux ne sont pas des chronos appariés du même
  athlète. Prendre le meilleur temps de chaque tableau ne démontre donc pas une
  loi de fatigue d’un athlète réel et ne permet pas de l’ajuster rigoureusement.
- Le modèle inter-distance est une estimation complémentaire, pas une loi
  entièrement apprise dans le classeur.

Calcul actuel dans core.mjs :
1. Construire un profil générique de log(temps) en fonction de log(distance),
   par morceaux entre 50, 100, 200, 400, 800 et 1500 m.
2. Sous 100 m, exposant 0,90 : hypothèse d’accélération initiale.
3. Entre les bornes suivantes, utiliser les rapports médians de vitesse KsA :
   100→200 : 0,992446 ; 200→400 : 0,912 ; 400→800 : 0,887940 ;
   800→1500 : 0,921097.
   Le rapport de temps correspondant est (distance2/distance1) / KsA.
   Source des coefficients indiquée dans le projet :
   https://pmc.ncbi.nlm.nih.gov/articles/PMC12181339/
4. À chaque chrono connu, calculer le résidu :
   r(d) = ln(chrono réel à d) - profil générique ln(temps à d).
5. Entre deux distances personnelles connues, interpoler les résidus selon
   ln(distance), puis les ajouter au profil générique et exponentier.
6. En dehors des distances personnelles connues, conserver le résidu du point
   connu le plus proche et suivre le profil générique pour extrapoler.
7. À une distance renseignée exactement, renvoyer le chrono personnel sans
   approximation. Afficher la provenance : mesuré, interpolé ou extrapolé.

Formules de cible à une distance d :
  t_ref = chrono exact ou estimé à la distance d
  v_ref = d / t_ref
  v_cible = v_ref × pourcentage / 100
  t_cible = d / v_cible = t_ref / (pourcentage / 100)

Important : la dernière division ressemble à la règle de trois initiale, mais
elle est correcte à distance fixée pour un pourcentage de vitesse. La correction
de fatigue porte sur la référence estimée d’une distance à l’autre : ne pas
revenir à t_ref × distance demandée / distance connue sans modèle de fatigue.

Pourcentages libres : strictement supérieurs à 0 et au plus 150 %, avec raccourcis
80, 85 et 89 %. Une intensité au-delà de 100 % reste techniquement possible ; elle
ne doit pas être présentée comme une performance physiologiquement garantie.
Calcul inter-distance limité actuellement à 50–1500 m. Le serveur accepte des
distances de consigne plus grandes, mais cela ne signifie pas qu’une référence
personnalisée est calculée en dehors de la plage du modèle.

Affichage des chronos au centième ; arrondir correctement lorsqu’un chrono
franchit une minute. Vitesse affichée en m/s, avec virgule décimale française.
Sans chrono personnel, ne pas inventer une cible personnalisée.
L’interpolation/extrapolation est une aide ; les consignes du coach restent prioritaires.

Incohérences du classeur relevées et corrigées seulement dans les calculs du site :
- Les 10 lignes du bloc 500 m à 85 % utilisent en réalité 80 %.
- Un en-tête 250 m à 85 % correspond à un bloc calculé à 89 %.
Le site applique le pourcentage choisi plutôt que reproduire ces erreurs de copie.
Les pourcentages ambigus du texte d’une séance ne sont pas convertis arbitrairement
en cibles structurées sans distance/référence explicite.

Autre incohérence conservée en note : la séance du 1er octobre indique « (800) »
alors que 2×250 + 2×200 totalise 900 m. Le texte source n’a pas été réécrit.

Plages de temps fixes :
- Le coach peut entrer une distance, une borne basse, une borne haute, une étiquette.
- Exemple de demande : 400 m entre 1:30 et 1:35 pour les filles, entre 1:10 et 1:20
  pour les gars. Ce sont des consignes, pas des valeurs à substituer aux records.
- Toutes les plages sont visibles ; le site ne déduit pas le sexe/groupe du membre.
- Si la courbe personnelle est disponible : intensité équivalente minimale =
  100 × t_ref / borne haute ; maximale = 100 × t_ref / borne basse.
- Une consigne peut combiner des cibles en pourcentage et des intervalles fixes.


9. COMMENTAIRES ET DIFFICULTÉ RESSENTIE
====================================

Interface compacte : bouton Commenter sur la séance ; fenêtre masquée sinon.
Champs : difficulté 1 à 5 étoiles et texte libre. Au moins un champ doit être rempli.
Échelle : 1 Très facile ; 2 Facile ; 3 Modéré ; 4 Difficile ; 5 Très difficile.
Un commentaire peut contenir seulement une note ou seulement du texte.
Limite de texte actuelle : 4000 caractères.

Un membre dispose d’un commentaire par séance, modifiable et supprimable par lui.
Commentaires permis sur les séances passées et futures.
Ils sont attachés à l’id de séance et non uniquement à sa date.
Une séance archivée n’est plus affichée dans les retours actifs de l’interface.

Visibilité :
- Public au groupe par défaut.
- Case « Réservé à moi et aux coachs » pour rendre TOUT le commentaire privé,
  texte ET difficulté. Pas de confidentialité limitée au texte seulement.
- Privé visible par l’auteur et les profils coach ; pas par les autres athlètes,
  ni par les admins simplement parce qu’ils sont admins.
- Filtrage dans l’API avant envoi au navigateur ; ne pas envoyer les données
  privées à tous les comptes pour les masquer ensuite en CSS.

Synthèse sur la séance : barre/moyenne publique de difficulté de 1 à 5, nombre
de votes, libellé lisible. Ne compter que les notes des commentaires publics.
Les commentaires sans note et les notes privées n’entrent pas dans cette moyenne.
Si aucun vote public : pas de moyenne inventée.
Les membres ne peuvent pas modifier les commentaires des autres, même coachs.


10. COMPÉTITIONS PARTAGÉES ET INSCRIPTIONS
========================================

Tout membre connecté peut ajouter, modifier, déplacer ou retirer une compétition,
y compris celle d’un autre membre. C’est une exception explicite aux droits
d’édition réservés au coach pour les autres éléments du planning.

Champs : nom obligatoire ; soit semaine ISO, soit date précise ; lieu facultatif ;
niveau facultatif. Valeurs actuelles de niveau : départemental, régional,
interclubs, national, international, meeting, autre, non renseigné.
Un lieu ou un niveau manquant n’empêche pas d’afficher la compétition.
Pour la date : au moins une semaine est requise dans l’implémentation actuelle.
La demande de dates « imprécises » est satisfaite par la semaine, pas par un
événement entièrement sans semaine et sans date.

Affichage :
- Dans la frise annuelle, toujours sur sa semaine, même si le jour précis est connu.
- Dans l’onglet Compétitions, sous forme de liste/tableau.
- Dans le mois : marqueur au jour précis, ou rappel de semaine si jour inconnu.
- Plusieurs compétitions dans une même semaine sont autorisées.
- La frise inclut aussi les compétitions placées avant/après la plage initiale.

Ligne attendue dans la liste : nom ; date/semaine ; lieu ; niveau ; case
Inscription ; bouton Inscrits ; modification.
Les données initiales importées de l’ancienne frise et des séances Compétition
ont été reprises en enregistrements dédiés sans inventer de jour exact.

Inscription :
- La case ajoute seulement la personne actuellement connectée.
- Athlètes, coachs et admins peuvent s’inscrire.
- Décocher retire son inscription.
- Le bouton Inscrits ouvre la liste des membres inscrits, publique dans le groupe.
- Ce n’est pas une inscription fédérale/officielle auprès de l’organisateur.
- Les inscriptions ne donnent aucun droit de modification des périodes ou séances.

Les compétitions sont des objets partagés indépendants des comptes de leurs auteurs.
Supprimer le compte d’un auteur ne supprime pas automatiquement ses compétitions.
Les séances de type Compétition sont reliées par sourceSessionId lorsqu’importées
ou synchronisées ; conserver cette relation lors d’évolutions, sans supposer que
toute compétition doit obligatoirement être une séance d’entraînement.

14. DONNÉES, API ET CONTRÔLES DE CONCURRENCE
=========================================

Base de production : D1, accessible par le binding Pages nommé exactement DB.
Le nom affiché de la base peut être equipe-athle ; vérifier la liaison existante
dans Cloudflare au lieu de supposer qu’une base de même nom est la bonne.

Principales tables :
- users : id, identifiant dans email, identité, rôle, chronos dans profile JSON,
  versions de profil/compte, coordonnées, rôle précédent.
- auth : jetons de session hachés, utilisateur, expiration ; le local ajoute csrf.
- records : collection, id, data JSON, version, archived.
  Collections : sessions, library, info, season, competitions.
- meta : marqueurs d’initialisation/migration et compteur revision partagé.
- role_events : journal des changements de rôles.
- account_credentials : mot de passe dérivé, état provisoire, version ; ancien
  identifiant capturé seulement pour la transition des comptes préexistants.
- group_access_codes : codes courants du groupe et coach, versionnés dans un
  enregistrement partagé. Les valeurs initiales sont `NOUVEAU` et `COACH`.
  Seuls les comptes admin reçoivent les valeurs courantes dans /api/state.
- account_created : user_id et date de création connue ; pas de dates fabriquées.
- session_comments : séance + auteur, difficulté, texte, confidentialité, version.
- competition_signups : compétition + utilisateur, date de son inscription.

Routes utiles, préfixe /api :
- GET /auth ; POST /setup ; POST /register ; POST /login ; POST /logout.
- GET /state : état filtré selon le rôle, profil personnel et contenus actifs.
- PUT /profile : ses chronos ; PUT /account : son identité ; DELETE /account.
- PUT /password : son mot de passe.
- PUT /account/coach : demande/retrait de son propre rôle coach ; le code coach
  exact est exigé côté serveur pour passer d’athlète à coach.
- PUT /access-codes : remplacer les deux codes, réservé admin et protégé par
  version ; le remplacement rend les anciennes valeurs immédiatement invalides.
- PUT /members/:id/admin : attribution/retrait admin, réservé admin.
- PUT /members/:id/coach : attribution/retrait coach, réservé admin.
- PUT /members/:id/password : nouveau mot de passe choisi, réservé admin.
- DELETE /members/:id : suppression ciblée, réservé admin.
- PUT /season : périodes et charges, réservé coach.
- POST /sessions, /library, /info ; PUT et DELETE /collection/:id : coach.
  L’échange de séances passe par la mise à jour avec swapId et swapVersion.
- PUT ou DELETE /sessions/:id/comment : uniquement son commentaire.
- POST /competitions ; PUT ou DELETE /competitions/:id : tout profil connecté.
- PUT /competitions/:id/signup : uniquement son inscription.

Principes :
- Les routes ne doivent jamais faire confiance à un userId fourni par le client
  pour modifier un profil/commentaire/inscription d’un autre membre.
- /api/register exige le code de groupe exact ; une inscription coach exige aussi
  le code coach exact. La casse et les espaces sont comparés sans normalisation.
- Les codes d’accès sont partagés, visibles uniquement par les admins dans leur
  état API, et modifiables uniquement par eux. La mise à jour est globale et
  versionnée ; la nomination d’un coach par un admin reste une action admin.
- La session serveur fournit l’identité et le rôle autorisé.
- Données validées côté serveur : dates réelles, champs, types, bornes, pourcentages,
  chronos positifs, formats des commentaires et versions.
- Identifiants stables même si une date, un nom ou un identifiant de connexion change.
- Version d’un objet/profil vérifiée avant modification ; conflit explicite plutôt
  qu’écrasement silencieux d’une modification concurrente.
- Transactions pour les échanges, actions groupées et suppressions ciblées.
- La réinitialisation admin ne touche ni profile ni profile_version des chronos.
- Les données privées doivent être filtrées avant la réponse JSON.

Synchronisation : réinterrogation environ chaque minute et au retour dans l’onglet.
Ce n’est pas du temps réel WebSocket. Les formulaires ouverts ne sont pas écrasés.
Les pages Chronos/Réglages peuvent différer leur rendu pour préserver la saisie ;
quitter/revenir sur la page peut être nécessaire pour voir un tableau actualisé.
Une session supprimée/réinitialisée est rejetée au prochain appel serveur.


15. HÉBERGEMENT ET MISE EN LIGNE
==============================

Solution retenue : GitHub + Cloudflare Pages + Pages Functions + D1.
La connexion Git du projet Cloudflare existe déjà selon la conversation.
Ne pas créer une nouvelle application ou une nouvelle base pour chaque modification.

Configuration de référence :
- Dépôt : MaylisCh/equipe-athle ; branche de production : main.
- Commande de build : npm run build.
- Dossier public de sortie : dist.
- Répertoire functions/ reconnu pour les fonctions Pages.
- Binding D1 de l’environnement : DB, lié à la base persistante existante.
- Les bindings sont gérés dans le tableau de bord Cloudflare.
- Ne pas réintroduire un wrangler.toml/configuration imposant une autre base
  sans vérifier la configuration active et la nécessité de ce changement.
- Node de build et version du bundler peuvent différer du Node du Mac.

Incident historique important : le bundler Pages utilisé avait refusé :
  import seed from '../../seed.json' with { type: 'json' };
Erreur : Expected ';' but found 'with'.
La forme compatible actuelle dans la fonction est :
  import seed from '../../seed.json';
Le test Node adapte cet import pour tester le handler. Ne pas réintroduire
automatiquement les attributs d’import JSON dans le fichier Pages sans vérifier
le bundler de production, même si cette syntaxe marche avec le Node local.

Le build ne publie que la coque, les modules client, CSS, logo et manifeste.
Les documents Excel/Word, la base SQLite locale, secrets, sources du serveur et
ce cahier des charges ne doivent pas être copiés dans le répertoire public.

Forfait gratuit : c’est un objectif, pas une promesse de limites immuables.
Le README historique cite 500 Mo par base, 5 Go au total, 5 millions de lignes
lues et 100 000 lignes écrites par jour. Ces chiffres ne sont pas revérifiés
dans ce document : consulter les limites D1/Workers officielles et le tableau
de bord du compte avant de conseiller une capacité ou de diagnostiquer un quota.
Ne pas mettre en place une purge automatique des séances pour répondre aux quotas.

Procédure courante de publication :
1. Vérifier le vrai dossier du dépôt et la branche main.
2. Modifier le code en préservant les changements existants et les données.
3. Lancer les tests pertinents et npm run build.
4. Vérifier git diff, ne sélectionner que les fichiers réellement concernés.
5. Créer un commit descriptif si la demande inclut la préparation du push.
6. Dans GitHub Desktop, l’utilisatrice clique sur Push origin.
7. Suivre le déploiement Pages et vérifier l’adresse en ligne.
8. Conserver le binding DB et confirmer l’absence de perte de données.

Ne pas annoncer « en ligne » après un simple commit local. Donner le commit et
la branche, distinguer commit préparé, push effectué et déploiement réussi.
Le site peut être entretenu en ligne pour les contenus, sans modifier le code.
Les évolutions techniques restent des modifications du dépôt suivies d’un build.

PWA : sur iPhone/iPad, Safari → Partager → Sur l’écran d’accueil ; sur Android,
option Installer/Ajouter à l’écran d’accueil du navigateur. La PWA n’est pas une
application native séparée. L’accès aux données et la connexion nécessitent le
serveur ; le cache de fichiers ne garantit pas un mode hors ligne complet.

- Conserver la compatibilité entre API locale et API Cloudflare pour toute nouvelle
  fonctionnalité ; favoriser les fonctions communes lorsque c’est possible.
- Mettre à jour le cache du service worker lors de changements client significatifs.
- Ajouter tout nouveau fichier client nécessaire à la liste du build, sans
  élargir la publication à tout le dépôt.
- Ne pas modifier le comportement d’authentification/rôles par simple commodité
  sans une consigne explicite de l’utilisatrice.

Migrations :
- Ajouter des tables/champs sans effacer les comptes existants.
- Utiliser des marqueurs de migration et insertions conditionnelles idempotentes.
- Réexécuter une migration ne doit ni remettre les mots de passe provisoires,
  ni restaurer une compétition archivée, ni écraser une séance éditée.
- L’initialisation de seed.json concerne une base neuve. La migration ponctuelle

18. LIMITES ACTUELLES ET ÉVOLUTIONS NON RÉALISÉES
==============================================

Ne pas confondre exigences, existant et pistes possibles :
- Dates de création historiques : inconnues si non stockées à l’époque.
- Heure de création : timestamp stocké pour les nouveaux comptes, mais pas
  affiché actuellement dans l’annuaire.
- Périodes/charges : édition bornée à S105 ; mois et compétitions plus extensibles.
- Modèle de fatigue : approximation d’aide ; pas une garantie physiologique et
  pas un entraînement statistique sur des chronos appariés du classeur.
- Rôles : exclusifs, pas de combinaison admin+coach actuelle.
- Inscription : code de groupe requis ; code coach exigé pour demander ce rôle.
- Les rôles restent exclusifs ; un admin n’est pas automatiquement coach.
- Codes de départ : `NOUVEAU` et `COACH`. Ils doivent être changés par les admins
  dans Réglages dès qu’ils souhaitent remplacer les valeurs communes.
- Synchronisation : interrogations périodiques, pas diffusion instantanée.
- Hors ligne : coque statique en cache, pas édition/synchronisation hors ligne.
- Inscription compétition : interne au groupe, pas inscription officielle.
- Réinitialisation : gérée par admin, pas de parcours de récupération par e-mail
  prévu dans les demandes réalisées.
- Aucune fonctionnalité de notification push, paiement, présence systématique,
  résultats de compétitions ou export fédéral n’a été demandée comme réalisée.
- Aucun effacement automatique pour gérer les quotas de stockage.
- Nommer un admin ne transmet pas le compte GitHub ni le compte Cloudflare.

Toute nouvelle évolution doit respecter le socle ci-dessus et être distinguée
de ce qui est déjà livré. Si elle nécessite un choix structurant, demander à
l’utilisatrice plutôt qu’en déduire une autorisation implicite.
